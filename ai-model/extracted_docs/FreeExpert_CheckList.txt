Présentation du rapport d’audit
Ce rapport présente les résultats de l’audit de sécurité réalisé sur FreeExpert, en s’appuyant sur les différentes catégories de la checklist des risques applicatifs critiques, allant de A01 à A10.
L’objectif est d’analyser progressivement chaque volet de la checklist afin d’identifier, documenter et prioriser les failles de sécurité réellement observées dans le code source, la configuration applicative et l’environnement serveur du projet.


Méthodologie de documentation
Pour chaque catégorie auditée, les failles confirmées sont présentées de manière structurée et homogène. Chaque constat contient les éléments suivants :
* Nom de la vulnérabilité 
* Catégorie concernée de la checklist 
* Description de la faille 
* Cause identifiée 
* Impact potentiel 
* Niveau de sévérité 
* Preuves techniques collectées 
* Commentaires d’analyse 
* Solution proposée


Objectif du rapport
Ce rapport vise à regrouper les vulnérabilités confirmées dans le cadre de l’audit du FreeExpert, en s’appuyant sur des preuves concrètes issues du code, de la configuration ou de l’environnement serveur.
Les recommandations proposées sont formulées de manière ciblée et adaptée au contexte du projet, avec l’objectif de renforcer la sécurité de la plateforme sans perturber son fonctionnement existant.










Audit du volet A04:2025 — Cryptographic Failures
Nous commençons l’analyse par le volet A04:2025 — Cryptographic Failures, qui couvre les faiblesses liées à la protection des secrets, des tokens d’authentification, des clés applicatives et des données sensibles.


A04-1 — Stockage en clair des tokens mobiles et validation directe en base


Élément
	Détails
	Nom du vulnérabilité
	Faille A04-1 : Validation du Mobile API Token par lookup direct en base
	Catégorie 
	A04:2025 — Cryptographic Failures 
	Description
	* Le token d’authentification mobile est utilisé comme secret d’accès à l’API mobile.
* Ce token est généré côté serveur puis stocké directement dans la colonne mobile_tokens.token.
* Le token reçu dans le header Authorization: Bearer <token> est comparé tel quel avec la valeur stockée en base.
* Aucune protection par hash cryptographique n’est appliquée avant le stockage du token. 
	Cause
	* La méthode de validation effectue une recherche directe avec where('token', $token).
* Le mécanisme ne stocke pas d’empreinte cryptographique du token, comme hash('sha256', $token).
* La base conserve donc une valeur directement réutilisable pour l’authentification API. 
	Impact
	* Si la base de données est compromise, les tokens mobiles encore valides peuvent être récupérés. 
* Un attaquant pourrait réutiliser un token extrait pour appeler directement l’API mobile. 
* L’accès pourrait être effectué sans connaître le mot de passe de l’utilisateur concerné. 
	Sévérité
	Medium
	

* Preuves :         


  



  



  







Commentaires : 


* Les preuves montrent que le token mobile est généré avec Str::random(64), puis stocké directement dans la colonne mobile_tokens.token.
* La méthode findByToken() confirme que la validation repose sur une recherche directe en base via where('token', $token), sans comparaison avec un hash cryptographique.
* Le middleware MobileTokenAuth récupère le token depuis le header Authorization: Bearer <token>, ce qui confirme que cette valeur est utilisée directement comme preuve d’authentification API.
* La vérification SQL confirme que les valeurs stockées ont une longueur de 64 caractères et ne correspondent pas au format classique d’un hash SHA-256.
* Le champ expires_at limite la durée de validité du token, mais il ne protège pas la valeur stockée en cas de compromission de la base de données.






Solution Proposée : 
* But : renforcer la protection des Mobile API Tokens afin qu’un token extrait depuis la base de données ne puisse pas être réutilisé directement dans les requêtes API.
* Remplacer le stockage en clair du token par un stockage sous forme de hash cryptographique, par exemple avec hash('sha256', $plainToken).
* Retourner le token en clair uniquement une seule fois au client mobile lors de sa génération, puis ne conserver en base que son empreinte cryptographique.
* Adapter la méthode createToken() dans app/Models/MobileToken.php afin de stocker le hash du token au lieu de la valeur brute dans la colonne utilisée pour la validation.
* Adapter la méthode findByToken() afin de calculer le hash du token reçu dans le header Authorization: Bearer <token>, puis comparer ce hash avec la valeur stockée en base.
* Prévoir une migration progressive non cassante, par exemple en ajoutant temporairement une colonne token_hash, puis en renouvelant progressivement les anciens tokens.
* Conserver le contrôle d’expiration existant via expires_at, afin de limiter la durée d’utilisation des tokens mobiles.
* Supprimer toute journalisation partielle du token, notamment token_prefix, afin d’éviter l’exposition d’une partie du secret dans les logs.




Faille A04-2 : Stockage en clair et validation directe des tokens de réinitialisation de mot de passe
Élément
	Détails
	Nom du vulnérabilité
	Faille A04-2 : Stockage en clair et validation directe des tokens de réinitialisation de mot de passe 
	Catégorie 
	A04:2025 — Cryptographic Failures 
	Description
	* Les tokens de réinitialisation de mot de passe sont générés puis stockés directement dans la table password_resets. 
* Le token reçu lors de la réinitialisation est comparé tel quel avec la valeur stockée en base.
* Le flux seller utilise uniqid() pour générer le token, ce qui n’est pas adapté à un secret de sécurité.
* Le flux seller ne montre pas de contrôle d’expiration clair avant le changement du mot de passe. 
	Cause
	* La valeur brute du token est insérée directement dans la colonne password_resets.token.
* La validation repose sur une recherche directe avec where('token', $request->token).
* Aucun hash cryptographique du token n’est utilisé pour le stockage ou la comparaison.
* Le flux seller utilise une génération faible basée sur uniqid() au lieu d’une génération cryptographiquement forte. 
	Impact
	* En cas de compromission de la base de données, un token de reset valide peut être récupéré et utilisé directement.
* Cela peut permettre la réinitialisation non autorisée du mot de passe d’un compte.
* Le risque est plus élevé pour le flux seller si le token reste valide sans expiration stricte. 
	Sévérité
	Medium
	





* Preuves :         
  

  

  





Commentaires : 
* Les preuves montrent que le flux seller génère un token avec uniqid(), puis l’enregistre directement dans la colonne password_resets.token
* Le lien de réinitialisation seller contient ce même token, ce qui confirme que la valeur stockée en base correspond à une valeur directement utilisable dans le processus de reset.
* La validation du flux seller repose sur une recherche directe en base via where('token', $request->token), avant la mise à jour du mot de passe.
* Aucun contrôle d’expiration clair du token seller n’a été identifié dans la logique analysée avant le changement du mot de passe.
* Le flux API mobile utilise une génération plus forte avec Str::random(60) et applique une expiration de 5 minutes, mais le token reste stocké en clair dans password_resets.token
* La correction recommandée consiste à stocker uniquement un hash du token de reset en base, à utiliser une génération cryptographiquement forte pour tous les flux, et à appliquer une expiration stricte avant toute réinitialisation de mot de passe.
Solution Proposée : 
* But : renforcer la sécurité du mécanisme de réinitialisation de mot de passe afin qu’un token récupéré depuis la base de données ne puisse pas être utilisé directement pour changer le mot de passe d’un compte.
* Remplacer la génération du token seller avec uniqid() par une génération cryptographiquement plus forte, par exemple Str::random(64).
* Ne plus stocker le token de réinitialisation en clair dans la table password_resets
* Stocker uniquement une empreinte cryptographique du token, par exemple avec hash('sha256', $plainToken)
* Envoyer le token en clair uniquement dans le lien de réinitialisation transmis à l’utilisateur, puis ne conserver en base que son hash.
* Ajouter un contrôle d’expiration strict côté seller avant toute mise à jour du mot de passe, par exemple une durée de validité de 5 à 15 minutes.
* Conserver la suppression du token après utilisation afin d’empêcher sa réutilisation.
* Appliquer la même logique de protection sur les deux flux concernés : seller et API mobile, afin d’avoir un comportement homogène.


















































Faille A04-3 : Protection insuffisante du fichier .env et des copies de sauvegarde contenant des secrets


Élément
	Détails
	Nom du vulnérabilité
	Faille A04-3 : Protection insuffisante du fichier .env et des copies de sauvegarde contenant des secrets 
	Catégorie 
	A04:2025 — Cryptographic Failures 
	Description
	* Les permissions du fichier .env sont trop permissives pour un fichier contenant des credentials.
* Plusieurs copies de sauvegarde .env.backup-* sont présentes à la racine du projet.
* Certaines copies disposent de permissions encore plus ouvertes que le fichier .env principal. 
	Cause
	* Les permissions appliquées au fichier .env permettent la lecture par d’autres utilisateurs locaux.
* Des fichiers de sauvegarde de .env ont été conservés sans restriction suffisante. 
	Impact
	* En cas d’accès local non autorisé ou de compromission d’un compte système, les secrets applicatifs peuvent être lus. 
* Les copies .env.backup-* augmentent la surface d’exposition des secrets. 
	Sévérité
	Medium
	



















* Preuves :         


  



  



  







Commentaires : 


* Les preuves montrent que le fichier .env contient plusieurs secrets sensibles, notamment des clés applicatives, identifiants de base de données, clés AWS, secrets mail, clés Pusher et secrets d’intégration.
* Les permissions observées sur .env sont trop permissives pour un fichier contenant des credentials, car le fichier reste lisible par d’autres utilisateurs locaux du système.
* La présence de plusieurs fichiers .env.backup-* augmente la surface d’exposition, car ces copies peuvent contenir des secrets anciens ou encore valides.
* Certaines copies de sauvegarde disposent de permissions plus ouvertes que le fichier .env principal, ce qui renforce le risque d’accès local non autorisé aux secrets.
* Les tests HTTP réalisés n’ont pas montré d’exposition directe du fichier .env, ce qui constitue un contrôle positif.
* Le risque principal reste donc un risque local : en cas de compromission d’un compte système ou d’un accès au serveur, les secrets applicatifs pourraient être lus depuis le fichier .env ou ses copies.






Solution Proposée : 
* But : réduire le risque d’exposition des secrets applicatifs stockés dans .env et dans ses copies de sauvegarde.
* Restreindre les permissions du fichier .env afin qu’il ne soit lisible que par les utilisateurs ou services strictement nécessaires.
* Appliquer des permissions plus adaptées, par exemple 640 si le groupe applicatif doit lire le fichier, ou 600 si seul le propriétaire doit y accéder.
* Supprimer les copies .env.backup-* si elles ne sont plus nécessaires.
* Éviter de conserver des fichiers de sauvegarde contenant des secrets directement à la racine du projet.
* Garder uniquement un fichier .env.example sans valeurs sensibles réelles, avec des placeholders comme DB_PASSWORD=change_me.
* Vérifier régulièrement qu’aucun fichier .env, .env.backup, .env.old ou équivalent n’est présent dans un emplacement exposé ou accessible inutilement.
* Prévoir une rotation des secrets si les copies .env.backup-* contiennent des secrets actifs ou réutilisables.

Audit du volet A07:2025 — Authentication Failures 


Nous poursuivons l’analyse par le volet A07:2025 — Authentication Failures, qui couvre les faiblesses liées aux mécanismes d’authentification de l’application. Ce volet concerne notamment les processus de connexion, de validation d’identité, de gestion des sessions, de double authentification, de réinitialisation de mot de passe et de protection contre les tentatives répétées.


L’objectif de cette analyse est de vérifier si les mécanismes d’authentification du FreeExpert permettent de confirmer correctement l’identité des utilisateurs, de protéger les comptes sensibles et de limiter les abus sur les endpoints critiques. A07-1 : Faille 1 – Protection insuffisante du flux de double authentification 2FA    


Élément
	Détails
	Nom de la faille 
	A07-1 : Protection insuffisante du flux de double authentification 2FA  
	Catégorie 
	A07:2025 — Authentication Failures 
	Description
	* Le mécanisme de vérification 2FA repose sur des paramètres d’identification transmis directement par le client, notamment user_id et user_type. 
* Ces valeurs sont utilisées pour retrouver l’utilisateur concerné, puis pour valider le code 2FA. En cas de code valide, l’application génère directement un JWT pour l’utilisateur correspondant. 
	Cause
	* Le flux 2FA ne s’appuie pas sur un contexte d’authentification temporaire côté serveur permettant de lier la vérification 2FA à une tentative de connexion déjà validée. 
* À la place, l’identification de l’utilisateur est reconstruite à partir de paramètres fournis dans la requête. 
	Impact
	* Cette conception augmente le risque d’exploitation non autorisée du mécanisme 2FA, notamment en cas de manipulation des paramètres `user_id` et `user_type`, de tentatives répétées sur le code 2FA ou d’utilisation non contrôlée de la route de renvoi du code. 
* Le risque principal concerne le renforcement insuffisant d’une étape critique du processus d’authentification.
	Sévérité
	Medium
	Fichiers concernés 
	routes/api.php ; app/Http/Controllers/Api/MobileAuthController.php 
	







* Preuves :       


  



  



  







Commentaires : 


* Les preuves montrent que le mécanisme 2FA est bien présent dans l’application, mais que les routes /2fa/verify et /2fa/resend ne disposent pas de middleware dédié visible dans la déclaration des routes.

* Preuves :


  



  























Commentaires : 


* La fonction deleteOrder($id) côté seller récupère la commande avec ServiceOrder::query()->find($id), uniquement à partir de l’identifiant reçu.
* Aucun contrôle visible ne vérifie que le seller_id de la commande correspond au seller authentifié avant le lancement de la suppression.
* Après cette récupération, la fonction supprime plusieurs éléments liés à la commande, notamment les messages associés, l’éventuelle review, puis la commande elle-même via une requête SQL directe.
* Le risque est important, car un seller authentifié pourrait cibler une commande qui ne lui appartient pas si son identifiant est connu ou deviné.
* Cette faiblesse correspond à un risque de Broken Access Control / IDOR, car une action destructive dépend d’un identifiant contrôlé côté client sans vérification d’accès suffisante.












Solution Proposée : 
* Modifier la fonction deleteOrder($id) dans Seller/OrderController.php.
* Avant de lancer la suppression, récupérer la commande avec une condition qui vérifie qu’elle appartient bien au seller connecté.
* Vérifier que le seller_id de la commande correspond à l’identifiant du seller authentifié via auth:seller.
* Si la commande ne correspond pas au seller connecté, retourner une erreur 403 Unauthorized et arrêter le processus de suppression.
* Exécuter la suppression des fichiers, messages, review et de la commande uniquement après cette vérification.
* Comme la suppression finale de la commande est effectuée via une requête SQL directe sur la table service_orders, cette requête ne doit être exécutée qu’après validation du droit d’accès du seller sur la commande ciblée.
