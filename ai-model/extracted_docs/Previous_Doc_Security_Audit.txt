Faille 3 : Sessions/Tokens mobiles non invalidés après reset


Élément
	Détails
	Nom du vulnérabilité
	Maintien des tokens mobiles après réinitialisation du mot de passe
	Description
	Après un reset password via /reset-password, le mot de passe est mis à jour mais les tokens mobiles existants (MobileToken) ne sont pas révoqués.
	Cause
	La méthode resetPassword() met à jour password puis supprime l’entrée password_resets, sans suppression des entrées MobileToken.
	Impact
	Un attaquant possédant déjà un token mobile valide conserve l’accès au compte même après changement du mot de passe (Account Takeover persistant).
	Moyen de divulgation
	Réutilisation d’un Bearer token mobile obtenu avant reset pour continuer à appeler les endpoints protégés.
	

  

                  * L878–881 : Mise à jour du mot de passe via Hash::make().
                  * L883–884 : Suppression uniquement de password_resets.
                  * Aucune suppression des MobileToken (MobileToken::where(...)->delete()) n’est effectuée.
                  * Les tokens mobiles actifs restent valides après reset.
  

                  * L901 : Récupération du token via $request->bearerToken().
                  * L903–905 : Suppression uniquement du token courant via MobileToken::findByToken($token)->delete().
                  * Pas de révocation globale des tokens liés au user_id.


Solutions proposées : 
                  * Ajouter après la mise à jour du mot de passe (bloc Hash::make() lignes 878–881) dans resetPassword() la suppression globale des tokens mobiles de l’utilisateur :

ssl_certificate /etc/letsencrypt/live/projety.com/fullchain.pem;

Piste 1 — Restriction des permissions .env


Remarque : Ordre d’implémentation
                                 * Bien que les constats soient présentés selon le niveau de risque, l’ordre d’application des correctifs doit être adapté pour garantir la continuité de service.
                                 * L’alignement du groupe du fichier (Constat 3) doit être réalisé avant la modification des permissions (Constats 1 et 2), afin d’éviter tout impact sur le fonctionnement de l’application.


Constat 1 — Permissions excessives sur le fichier .env (lecture accordée à Others), (Faille de sécurité)
  
   


  
  



                                 * La permission 754 signifie que 7 (rwx) correspond aux droits du propriétaire (lecture, écriture, exécution), 5 (r-x) correspond aux droits du groupe (lecture, exécution), et 4 (r--) correspond aux droits des autres utilisateurs (lecture uniquement).


Risque sécurité : 
                                 * La permission 754, où le chiffre 4 correspond aux droits des “Others” (lecture uniquement), permet à tout utilisateur SSH non privilégié, non propriétaire et non membre du groupe, de lire le fichier en exécutant 
cat .env
Solution Proposée : 
                                 * Appliquer le principe du moindre privilège en restreignant l’accès au fichier .env uniquement au propriétaire du fichier et à l’utilisateur exécutant le service applicatif (ex : www-data), tout en supprimant l’accès des “Others”.
                                 * Il faut attribuer le groupe du fichier .env à l’utilisateur exécutant le service applicatif (www-data), car l’application tourne sous cet utilisateur et a besoin d’un accès en lecture.
Commande :    sudo chgrp www-data .env
- Il faut restreindre les permissions à 640, car cela conserve la lecture pour le propriétaire et le groupe tout en supprimant totalement l’accès des “Others”.
Commande :    sudo chmod 640 .env
                                 * L’état final sécurisé attendu doit être :  -rw-r----- 1 ubuntu www-data .env 












Constat 2 — Bit d’exécution activé inutilement sur un fichier texte   (Problème de configuration)
  
  
  



Commentaires : 
                                 * Le fichier .env possède le bit d’exécution actif (-rwxr-xr--).
                                 * Il s’agit d’un fichier texte (ASCII) ne nécessitant aucun droit d’exécution.
                                 * La présence du bit x est inutile et ne respecte pas le principe du moindre privilège.
                                 * Le risque d’exploitation directe est faible, mais cette configuration reflète une gestion permissive des permissions sur un fichier sensible.

Solution Proposée : 
                                    * Supprimer le droit d’exécution (x) du fichier .env, car c’est inutile pour un fichier de configuration.
                                    * Vérifier au préalable que .env n’est pas exécuté comme script :
Commande : 
grep -R --line-number -E '(\./\.env|source[[:space:]]+\.env|bash[[:space:]]+\.env|sh[[:space:]]+\.env)' . 2>/dev/null
                                    * Appliquer une correction (max safe) : supprimer uniquement le bit exécutable pour le propriétaire et le groupe, sans toucher aux droits de lecture/écriture existants :
Commande :      chmod u-x,g-x .env
                                    * Vérifier après application :
Commande :          stat -c '%a (%A)' .env
Résultat attendu : absence du bit x sur le fichier 
Constat 3 — Groupe du fichier .env non aligné avec l’utilisateur applicatif  (incohérence d’architecture des permissions)
  
  
  

Commentaires : 
                                    * Le fichier .env appartient au groupe ubuntu, alors que l’application s’exécute sous www-data, ce qui crée un désalignement entre le groupe du fichier et l’utilisateur applicatif.
                                    * L’accès actuel de l’application repose sur le droit accordé à Others (identifié comme faille dans le Constat 1).
                                    * Le réalignement du groupe (Constat 3) doit être effectué avant la suppression du droit Others (Constat 1), afin d’éviter toute interruption de service.
Solution Proposée : 
                                    * Aligner le groupe du fichier .env avec l’utilisateur exécutant le service applicatif (www-data) afin d’assurer un accès en lecture dédié et sécurisé.
                                    * Cette étape doit être réalisée avant la suppression du droit accordé à la catégorie Others (Constat 1), afin d’éviter toute interruption de service.
                                    * Commande :       sudo chgrp www-data .env
                                    * Vérification :        stat -c '%U:%G %a (%A)' .env
Résultat attendu :
Owner = ubuntu | Groupe = www-data | Permissions = 754 (-rwxr-xr--)

Architecture cible (JWT Access court + Refresh token en DB)


Le modèle cible utilise deux tokens : 
                                          * Un Access Token (JWT) généré à partir d’un payload et signé (non stocké en DB)
                                          * Un Refresh Token opaque généré aléatoirement, stocké en base sous forme hachée pour permettre rotation et révocation.
Élément
	Détails
	Access Token
	                                          * Type : JWT signé
                                          * Transport : Authorization: Bearer <access_jwt>
                                          * TTL : court (ex. 10–15 min)
                                          * Stockage DB : non
	Refresh Token
	                                          * Type : opaque aléatoire (non-JWT)
                                          * Stockage : DB (haché)
                                          * TTL : plus long (ex. 7 jours)
                                          * Rôle : générer un nouvel access + rotation
                                          * Liaison : 1 refresh par session/device
	

	Refresh (rotation)
	                                          * Le client appelle : POST /refresh (body : refresh_token)
                                          * Vérifie refresh en DB
                                          * Supprime l’ancien refresh
                                          * Crée un nouveau refresh
                                          * Retourne nouveau access_token (+ nouveau refresh_token)
	Multi-device
	                                          * 1 refresh par device/session
                                          * Plusieurs refresh possibles pour un même user
	API Call (auth)
	                                          * Le client envoie : Authorization: Bearer <access_token>
                                          * Le serveur valide : signature + expiration (sans DB)
                                          * Si access expiré : Refresh (rotation) puis relancer la requête
	Login
	                                          * Le serveur génère : access_token (JWT court) + <refresh_token> (opaque aléatoire)
                                          * Stocke : refresh_token haché en DB (lié à user + session/device)
                                          * Retourne au client : access_token + refresh_token (+ durée d’expiration de l’access)
	Logout
	                                          * Le client demande la déconnexion
                                          * Le serveur révoque : supprime le refresh token correspondant en DB
                                          * Le access_token devient inutilisable à la fin de son expiration (TTL court)
	



Roadmap de migration
Remarque 1 :
                                          * JWT sera introduit en parallèle dans un périmètre séparé à créer (versions v2 des routes existantes, ex. /api/v2/*), tout en gardant l’ancien mécanisme actif (mobile.auth / unified.auth).
                                          * Migration route par route (réduction du risque) : on bascule un petit groupe de routes v2 vers le middleware JWT (à créer, ex. jwt.auth) à la fois, pendant que toutes les autres routes continuent d’utiliser mobile.auth / unified.auth. Cela permet de tester et valider progressivement sans impacter toute l’API.
                                          * En cas de problème, le retour arrière se fait par rollback immédiat : désactiver /api/v2/* ou retirer jwt.auth au niveau des routes concernées pour revenir au flux acteul.




Remarque 2 :
                                          * La phase 0 n’est pas obligatoire pour démarrer la migration JWT (puisque JWT est introduit en parallèle sur des routes v2).
                                          * Elle est fortement recommandée car l’ancien mécanisme restera actif pendant la coexistence : ces actions réduisent immédiatement le risque et renforcent le durcissement de sécurité du mécanisme actuel.
                                          * Actions à faire : hasher les tokens en DB, réduire le TTL, supprimer les logs sensibles (token_prefix), supprimer les tokens déjà expirés, planifier la purge régulière des tokens expirés.

- Prolonger la période de transition et reprendre la migration client côté v2

 Faille  9 (Mass Assignment) : Modification non contrôlée des champs de configuration des sections de la page d’accueil


Élément
	Détails
	Nom du vulnérabilité
	Modification non contrôlée des champs de configuration des sections de la page d’accueil
	Description
	- Tous les champs de la requête sont transmis directement au modèle Section via update($request->all()).
- L’application ne limite pas explicitement les attributs modifiables.
- Un utilisateur peut tenter d’ajouter dans la requête des champs non prévus afin de modifier d’autres attributs du modèle.

- Le modèle Section déclare protected $guarded = [ ]; ce qui n’impose aucune restriction sur les attributs modifiables.
- Cette combinaison permet la mass assignment de tout champ envoyé dans la requête.
	Impact
	Modification non autorisée de champs de configuration des sections de la page d’accueil.
	Sévérité
	Medium
	

                                                   * Preuves :    
  



Commentaires :
                                                   * L18–L24 : SectionController.php : la méthode update() récupère l’enregistrement Section::query()->first() puis applique directement $sectionInfo->update($request->all()), ce qui transmet tous les champs reçus dans la requête au modèle sans filtrage explicite des attributs autorisés.
                                                   * L12–L17 : Section.php : le modèle déclare protected $guarded = [];, ce qui n’impose aucune restriction sur les attributs modifiables et permet la mass assignment de tout champ envoyé dans la requête.


Solution Proposée : 
                                                   * Utiliser $request->only([...]) et $fillable, car cette combinaison permet de restreindre explicitement les champs modifiables à ceux réellement attendus par la fonctionnalité et de bloquer les paramètres supplémentaires injectés dans la requête.
                                                   * Dans app/Http/Controllers/BackEnd/HomePage/SectionController.php, remplacer à la ligne 22 $sectionInfo->update($request->all()) par $sectionInfo->update($request->only([...])), afin de mettre à jour uniquement les champs autorisés de cette fonctionnalité.
                                                   * Dans app/Models/HomePage/Section.php, remplacer protected $guarded = []; à la ligne 17 par protected $fillable = [...]; afin de limiter les champs que le modèle accepte en mass assignment
Remarque :
                                                   * Les champs autorisés doivent être identiques dans $request->only([...]) et dans $fillable, afin que le contrôleur et le modèle appliquent la même restriction.
