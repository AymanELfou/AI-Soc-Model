	Mobile API Token stocké en clair
	Description

	Medium

Faille 4 ( HasPermission) : Vérification incorrecte des permissions dans le middleware HasPermission

	Détails
	Nom du vulnérabilité
	Vérification incorrecte des permissions dans le middleware HasPermission
	Description
	   * Le middleware HasPermission contrôle l’accès aux routes administratives via permission:*.
   * Si aucun rôle n’est associé à l’utilisateur admin ($role == null), l’accès est autorisé.
   * Dans ce cas, aucune vérification des permissions n’est effectuée.


	Cause
	La condition suivante autorise l’accès lorsque $role est nul :
`if (is_null($role)
	Impact
	   * Si un compte administrateur possède role_id = null, le rôle n’est pas récupéré.
   * Dans ce cas, les permissions ne sont pas vérifiées.
   * L’utilisateur pourrait accéder à certaines fonctionnalités administratives sans contrôle de permission.
	Sévérité
	Medium
	

   * Preuves :      


  



  





Commentaires : 
   * L31–L32 : HasPermission.php : la condition is_null($role) autorise la requête même si aucun rôle n’est associé à l’administrateur, sans vérifier les permissions.
   * L23–L24 : HasPermission.php : si role_id est nul, aucun rôle n’est récupéré et $role reste nul.

Avertissement avant implémentation de la solution proposée :
   * Pour éviter des blocages d’accès, il faut s’assurer que chaque administrateur dispose d’un rôle valide et des permissions appropriées avant mise en production.
   * Sans cette vérification, certains administrateurs peuvent perdre l’accès à certaines fonctionnalités.

   * Supprimer la partie is_null($role) || de la condition actuelle.
   * L’accès doit être autorisé uniquement si un rôle valide est associé à l’administrateur et que la permission demandée existe dans les permissions du rôle.
   * Remplacer le renvoi redirect()->back() à la ligne 35 par un refus d’accès explicite côté serveur (403 Forbidden).






 Faille 5 ( RBAC) : Absence de vérification d’appartenance de la commande dans storeMessage


Élément
	Détails
	Nom du vulnérabilité
	Absence de vérification d’appartenance de la commande dans storeMessage


	Description
	   * La méthode storeMessage permet d’ajouter un message à une commande à partir de son ID.
   * Elle ne vérifie pas que l’utilisateur qui soumet la requête en est le propriétaire légitime.


	Cause
	   * Aucun contrôle d’appartenance n’est effectué avant l’enregistrement du message.
   * La commande est récupérée directement via ServiceOrder::findOrFail($id).
   * MessageRequest n’applique pas de contrôle d’autorisation, car authorize() retourne true
	Impact
	Un utilisateur authentifié peut potentiellement ajouter un message à une commande tierce sans autorisation.
	Sévérité
	Medium
	





   * Preuves :      


  



  



Commentaires : 


   * L868 : UserController.php : la commande est récupérée directement via ServiceOrder::findOrFail($id) à partir de son ID, sans filtre d’appartenance visible dans la requête
   * L922–L926 : UserController.php : le message est associé à order_id = $id puis enregistré, sans vérification préalable que cette commande appartient bien à l’utilisateur qui soumet la requête.
   * L15–L18 : MessageRequest.php : authorize() retourne true et n’ajoute aucun contrôle d’autorisation pour compenser ce manque.
 
Avertissement avant implémentation de la solution proposée :
   * Avant d’ajouter le contrôle sur storeMessage, il faut confirmer quels utilisateurs doivent réellement pouvoir envoyer un message sur une commande.
   * Le but est de corriger l’accès non autorisé sans bloquer des utilisateurs déjà autorisés par la plateforme.
   * Sans cette vérification préalable, une correction trop stricte peut casser un fonctionnement valide et provoquer des 403 non souhaités après mise en production.
Solution Proposée : 
   * Dans app/Http/Controllers/FrontEnd/UserController.php, ajouter après la ligne 868 une condition qui vérifie que order->user_id == $user->id avant tout enregistrement du message.
   * Si cette condition échoue, interrompre immédiatement l’exécution de storeMessage avec un refus d’accès côté serveur, par exemple via abort(403).
   * Ce blocage doit être placé avant les lignes 918–926, car c’est à cet endroit que le ServiceOrderMessage est créé puis sauvegardé.
   * Si d’autres utilisateurs doivent aussi être autorisés à envoyer des messages sur une commande, intégrer leurs conditions d’accès dans le même contrôle avant de laisser la méthode poursuivre le traitement.

 Faille  9 (Mass Assignment) : Modification non contrôlée des champs de configuration des sections de la page d’accueil


Élément
	Détails
	Nom du vulnérabilité
	Modification non contrôlée des champs de configuration des sections de la page d’accueil
	Description
	- Tous les champs de la requête sont transmis directement au modèle Section via update($request->all()).
- L’application ne limite pas explicitement les attributs modifiables.
- Un utilisateur peut tenter d’ajouter dans la requête des champs non prévus afin de modifier d’autres attributs du modèle.
	Cause
	- Le contrôleur utilise update($request->all()), ce qui transmet tous les champs reçus au modèle.
- Le modèle Section déclare protected $guarded = [ ]; ce qui n’impose aucune restriction sur les attributs modifiables.
- Cette combinaison permet la mass assignment de tout champ envoyé dans la requête.
	Impact
	Modification non autorisée de champs de configuration des sections de la page d’accueil.
	Sévérité
	Medium
	

         * Preuves :    
  



Commentaires :
         * L18–L24 : SectionController.php : la méthode update() récupère l’enregistrement Section::query()->first() puis applique directement $sectionInfo->update($request->all()), ce qui transmet tous les champs reçus dans la requête au modèle sans filtrage explicite des attributs autorisés.
         * L12–L17 : Section.php : le modèle déclare protected $guarded = [];, ce qui n’impose aucune restriction sur les attributs modifiables et permet la mass assignment de tout champ envoyé dans la requête.


Solution Proposée : 
         * Utiliser $request->only([...]) et $fillable, car cette combinaison permet de restreindre explicitement les champs modifiables à ceux réellement attendus par la fonctionnalité et de bloquer les paramètres supplémentaires injectés dans la requête.
         * Dans app/Http/Controllers/BackEnd/HomePage/SectionController.php, remplacer à la ligne 22 $sectionInfo->update($request->all()) par $sectionInfo->update($request->only([...])), afin de mettre à jour uniquement les champs autorisés de cette fonctionnalité.
         * Dans app/Models/HomePage/Section.php, remplacer protected $guarded = []; à la ligne 17 par protected $fillable = [...]; afin de limiter les champs que le modèle accepte en mass assignment
Remarque :
         * Les champs autorisés doivent être identiques dans $request->only([...]) et dans $fillable, afin que le contrôleur et le modèle appliquent la même restriction.
